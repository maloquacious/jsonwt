# Differences from RFC 7519

This document compares jsonwt v1 with [RFC 7519, JSON Web
Token](https://www.rfc-editor.org/rfc/rfc7519.html), and outlines what a
standards-compliance project would require.

> **Project direction:** jsonwt is a learning tool for local development,
> examples, and tests. There are no plans to make it fully RFC 7519 compliant.
> Applications that need interoperable or production authentication should use
> a maintained JWT or OIDC implementation instead.

The outline below is explanatory, not a roadmap or promise of future features.
RFC compliance would not by itself make this package suitable for production;
key management, issuer trust, revocation, replay defenses, deployment controls,
and application authorization remain separate concerns.

## What RFC 7519 defines

RFC 7519 defines a JWT as a JSON object containing claims, carried as the
payload of a JSON Web Signature (JWS) or the plaintext of a JSON Web Encryption
(JWE). The compact representation and cryptographic processing are delegated
to the JOSE family of specifications, principally:

- [RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html) for JWS;
- [RFC 7516](https://www.rfc-editor.org/rfc/rfc7516.html) for JWE; and
- [RFC 7518](https://www.rfc-editor.org/rfc/rfc7518.html) for algorithms and
  key requirements.

Consequently, RFC 7519 compliance cannot be implemented by changing claim names
alone. A signed JWT implementation also has to implement the applicable JWS and
JWA requirements. JWE encryption and nested JWTs are optional in RFC 7519, so a
conforming implementation can limit itself to the JWS forms required by
[Section 8](https://www.rfc-editor.org/rfc/rfc7519.html#section-8).

## Difference summary

| Area | RFC 7519 and JOSE | jsonwt v1 | Compliance work |
| --- | --- | --- | --- |
| Purpose | Interoperable claims representation carried by JWS or JWE. | Small learning API with a stable custom wire contract. | Replace the custom contract rather than extending it invisibly. This would require a new major version. |
| Claims set | The payload JSON object is the JWT Claims Set; each top-level member is a claim and values can be any JSON value ([Sections 3–4](https://www.rfc-editor.org/rfc/rfc7519.html#section-3)). | Application data is JSON-marshaled, base64url-encoded again, and stored in one top-level string named `claim`. | Expose a general top-level claims model and encode private/public claims directly in the payload. |
| Header | A JOSE Header follows JWS or JWE rules. `typ` is optional; `cty` has defined nested-JWT behavior ([Section 5](https://www.rfc-editor.org/rfc/rfc7519.html#section-5)). | Uses JWS-like `alg`, `typ`, and `kid`, plus a private `ver`; unknown fields are discarded when re-signing and critical extensions are not modeled. | Implement JOSE header processing, including understood/ignored parameter policy and JWS `crit` handling; preserve or reject extensions deliberately. |
| Compact form | Signed JWTs use JWS Compact Serialization. Unsecured JWTs use `alg: "none"` and an empty signature segment ([Section 6](https://www.rfc-editor.org/rfc/rfc7519.html#section-6)). | Requires exactly three non-empty segments and supports only signatures produced by a configured `Signer`. | Implement the complete selected JWS profile. RFC 7519 Section 8 requires `HS256` and `none`; `none` should be disabled unless explicitly selected by trusted policy. |
| Algorithms | The application decides which algorithms are acceptable. RFC 7519 Section 8 defines implementation requirements; JWA defines each algorithm. | One built-in HS256 signer, selected by a factory and exact `alg` match; this is effectively a one-algorithm trusted binding. | Preserve that property while supporting explicit trusted allowlists and all required processing for the declared profile. Never let an untrusted header choose an algorithm or key without policy checks. |
| HS256 key | RFC 7518 requires an HMAC key at least as large as the hash output: 256 bits for HS256 ([RFC 7518 Section 3.2](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.2)). | Accepts any non-empty byte slice. | Reject secrets shorter than 32 bytes and add standard JWA test vectors. |
| Registered claims | `iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, and `jti` are optional registered claims whose required use is application-specific ([Section 4.1](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1)). | Stores these fields internally, but callers cannot generally set or read them; `iat` and `exp` are always required by validation. | Expose claim access and a validation policy that states which claims each application requires. Requiring `iat` and `exp` can remain a documented stricter application profile, but must not be presented as an RFC-wide requirement. |
| Audience | `aud` can be one case-sensitive StringOrURI or an array. If present, a processor not identified in it must reject the JWT ([Section 4.1.3](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.3)). | Decodes only an array of strings and does not enforce an expected audience. | Accept both representations and require trusted expected-audience policy when `aud` is present. |
| NumericDate | `exp`, `nbf`, and `iat` are JSON numbers representing seconds since the epoch; non-integer values can be represented ([Section 2](https://www.rfc-editor.org/rfc/rfc7519.html#section-2)). | Uses integer Unix seconds only. | Parse the full NumericDate representation or explicitly define and test a narrower interoperable profile. |
| Time validation | `exp` is exclusive and `nbf` is inclusive; small clock-skew leeway is optional. `iat` identifies issue time but RFC 7519 does not itself require rejecting future `iat` values. | Uses the same `exp` and `nbf` boundaries, permits no leeway, and also rejects a token before `iat`. | Keep the correct boundaries, add policy-controlled leeway, and make any future-`iat` restriction an explicit application policy rather than a general RFC rule. |
| String values | `iss`, `sub`, and audience values use case-sensitive StringOrURI comparison without canonicalization; values containing `:` must be URIs ([Section 2](https://www.rfc-editor.org/rfc/rfc7519.html#section-2)). | Does not expose or apply application validation for these values. | Implement exact comparison and URI-shape rules in claim policy. |
| Validation | RFC 7519 Section 7.2 requires JOSE header parsing, supported-parameter checks, JWS/JWE validation, claims-set JSON validation, and rejection on any failed step. | Decodes a fixed struct, checks `alg`/`kid`, verifies one signature, and enforces package time rules. | Implement the complete RFC 7519/JWS validation pipeline and distinguish syntax, JOSE, cryptographic, and application-claim failures. |
| Media type | Registers `application/jwt` and `urn:ietf:params:oauth:token-type:jwt` ([Sections 9–10](https://www.rfc-editor.org/rfc/rfc7519.html#section-9)). | Makes no media-type or token-type claim. | Emit those identifiers only for values that satisfy the selected JWT profile. |
| Encryption and nesting | JWE and nested JWT support are optional; nested content uses `cty: "JWT"`. | Supports neither. | No work is required for a signed-only profile; otherwise implement RFC 7516 and nested validation end to end. |

Some current choices are narrower application rules rather than standalone RFC
violations. For example, an application may require `exp`, use only HS256,
define a private claim named `claim`, and define a private `ver` header under
the JOSE extension rules. Integer-only parsing, array-only `aud`, missing
audience policy, and incomplete JOSE processing are separate interoperability
gaps. Taken together with the opaque API, these choices mean jsonwt cannot
claim general JWT interoperability. A token that happens to be accepted by
another library is not evidence of compliance.

## Steps a compliance project would need

### 1. Define the supported JWT profile

Decide whether the implementation supports signed JWS JWTs only or also JWE and
nested JWTs. List supported algorithms, header parameters, registered claims,
required application claims, clock-skew policy, and unsecured-JWT policy.

For a modern implementation, reconcile RFC 7519's original implementation
requirements with [RFC 8725, JSON Web Token Best Current
Practices](https://www.rfc-editor.org/rfc/rfc8725.html). In particular, callers
must select acceptable algorithms through trusted configuration; the token's
`alg` value must never be treated as authority to choose a verification method.

### 2. Replace the opaque claim representation

Introduce a JWT Claims Set abstraction that preserves arbitrary top-level JSON
claims. Registered claims need standards-compatible types, while public and
private claims need collision-aware names and arbitrary JSON values. Remove the
inner base64 encoding of application data and place those claims directly in
the payload object.

This changes both the API and wire format and therefore cannot be done
compatibly within jsonwt v1.

### 3. Implement JOSE parsing and serialization

Use JWS Compact Serialization for signed tokens and follow RFC 7515 for exact
base64url, protected-header, payload, and signature processing. Parse JOSE
parameters before use, reject unsupported critical parameters, and preserve
the exact protected bytes used as signature input. If unsecured JWTs are in
scope, accept the required empty third segment only under explicit trusted
policy.

If encryption is in scope, implement RFC 7516 rather than adding encryption to
the current three-segment structure. JWE compact values use five segments.

### 4. Implement algorithms as specified by JWA

Enforce key type and minimum key size for every algorithm. For HS256, require a
secret of at least 256 bits. Bind each key to the algorithms it is allowed to
use, compare MACs in constant time, and select keys only from trusted local or
remotely authenticated configuration. Additional algorithms require their own
JWA encoding, key, and verification rules; they cannot be added through a name
string alone.

### 5. Separate cryptographic validation from claim policy

After successful JWS/JWE processing, validate that the payload is a JSON object
with acceptable duplicate-name behavior. Then apply an explicit application
policy for issuer, subject, audience, expiration, not-before, issue time, token
ID, required private claims, and allowed clock skew. Unknown claims must remain
available or be ignored as RFC 7519 permits; they must not silently change the
signed bytes.

### 6. Build interoperability and negative test suites

Tests would need to include:

- RFC 7519 and RFC 7515 examples and JWA algorithm vectors;
- tokens exchanged with independent maintained JWT implementations;
- single-string and array `aud` values;
- integer and fractional NumericDate values;
- optional and required registered-claim combinations;
- duplicate claims, malformed UTF-8/JSON/base64url, and unknown or critical
  JOSE parameters;
- algorithm/key confusion attempts, altered signatures, weak HS256 keys, and
  unsecured tokens under enabled and disabled policies; and
- exact `exp` and `nbf` boundaries with configured clock skew.

Passing self-generated round trips would not be sufficient because producer
and consumer can share the same non-standard assumption.

### 7. Document the conformance claim and security boundary

Documentation would need to name the implemented RFCs and profile, list every
unsupported optional feature, define media types, and state application-policy
requirements. A security review would still be required before recommending
the implementation across a trust boundary.

## Why jsonwt will remain intentionally different

The compliance work above would replace the project's small teaching model
with a JOSE implementation, a general claims system, policy configuration, key
constraints, interoperability maintenance, and a much larger security surface.
That is valuable work for a production JWT library, but it conflicts with this
project's purpose.

jsonwt therefore keeps its custom v1 format and does not describe its values as
standards-compliant JWTs. Use the [token format reference](token-format.md) for
the contract it does provide and [Security and scope](security.md) for the
environments where that contract is appropriate.
